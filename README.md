# Азим Чарыев — сайт-портфолио

Вёрстка по макету Figma [«Вариант 3»](https://www.figma.com/design/i5ztFGxGY4Sb11k01AVjZc/Charyev?node-id=156-1391).
Стек: Vite + React + TypeScript, без UI-библиотек.

## Запуск

```bash
npm install
npm run dev
```

```bash
npm run build
```

Сборка кладётся в `dist/` — это статика, её можно залить на любой хостинг.

## Оптимизация видео

Оригиналы съёмок лежат в `src/assets/cases` и `src/assets/gallery`, но в git не
попадают — они весят под гигабайт и в вёрстке не используются. Сайт берёт
только облегчённые копии из `src/assets/optimized`:

- `thumb` — 270 px, 20 FPS. Только карточки Hero;
- `preview` — 540 px, 20 FPS. Лента кейсов и отдельные ролики на странице
  кейса — там самый крупный слот 382 px;
- `detail` — 720 px, 25 FPS. Крупные слоты страницы кейса (~360 px, то есть с
  запасом под retina).

**Почему у Hero свой размер.** Его карточки показывают видео шириной 82–135 px,
и 540-пиксельные превью означали в 16–43 раза лишней работы на кадр — по
площади. Карточек четырнадцать, играют одновременно, и этот перерасход был
главной причиной подлагивания: 7,26 млн пикселей в декоде на кадр при 421
тысяче реально показанных. Пул вынесен в `src/data/heroMedia.ts` и намеренно
отвязан от `caseDetails.ts`: Hero берёт кадры вперемешку и не привязан к
конкретным кейсам, а тянуть пути оттуда значило бы тащить и их размер.

**Дальний план не играет.** Восемь из четырнадцати карточек размыты на 9 px и
притушены до 46% — движения там почти не разобрать, зато каждый их кадр
заставлял пересчитывать размытие. Они держат стоп-кадр (`still` у
`SilentVideo`), поэтому размытие считается один раз. Вместе с уменьшением
размера это снизило декод в 9,3 раза: 6 роликов по 129 600 пикселей вместо 14
по 518 400.

Главный рычаг веса — не кодек, а длительность. Ролики на сайте немые, без
контролов и крутятся бесконечным лупом, поэтому полная длина исходника не
нужна: скрипт берёт первые 12 секунд. Суммарные 9,6 минуты давали 60 МБ; после
обрезки то же качество (те же CRF, но `preset veryslow`) укладывается в
17,5 МБ — 7,8 МБ `preview` и 9,7 МБ `detail`.

Пересобрать копии после замены исходников:

```powershell
.\scripts\optimize-videos.ps1
```

FFmpeg приезжает вместе с `npm install` (пакет `ffmpeg-static`), отдельно
ставить не нужно — чужую сборку можно подсунуть ключом `-FfmpegPath`. Общая
длительность меняется ключом `-Duration`, а точка входа для конкретного ролика
— полем `Start` в таблице внутри скрипта: если у ролика неудачное начало,
правится только это поле.

Скрипт удаляет аудиодорожки, добавляет `faststart` и пропускает уже готовые
файлы. Чтобы пересобрать один ролик, удалите его копию из
`src/assets/optimized` и запустите команду снова; чтобы пересобрать всё —
ключ `-Force`.

**Грабли:** ролики Николая приехали с macOS, а там имена файлов лежат в NFD —
`й` записан как `и` + U+0306. Точно такая же на вид строка в коде записана в
NFC, поэтому поиск по имени сначала молча ничего не находил. В
`Find-NikolayVideo` обе стороны приводятся к NFC перед сравнением.

## Как устроено масштабирование

Макет нарисован под ширину **1728 px**. Вместо ручной адаптации введена
единица `--px` — «один пиксель макета»:

```css
.page { --px: calc(min(100cqw, 1920px) / 1728); }
```

Все размеры записаны как `calc(<число из Figma> * var(--px))`, поэтому на
десктопе страница повторяет макет один в один при любой ширине окна и
упирается в потолок на 1920 px.

## Мобильная раскладка

Включается не по ширине, а по `@media (orientation: portrait)` — весь
портретный блок живёт в `src/styles/responsive.css`. Мобильный макет нарисован
под ширину **440 px** ([Figma, node 278:2304][mobile]), и у него своя единица:

```css
.page { --mpx: calc(min(100cqw, 440px) / 440); }
```

`--mpx` — «один пиксель мобильного макета», ровно та же идея, что `--px`, но
другая база. Выше 440 раскладка не растягивается, а встаёт колонкой по центру:
иначе на планшете в портрете карточка услуг упиралась бы в свои 400, а Hero и
футер разъезжались на всю ширину.

Кегли пишутся как `max(<пол>, calc(N * var(--mpx)))`. Чистая пропорция на
320 px ужимает текст до нечитаемого — 16 px макета превратились бы в 11,6.

**Главные грабли.** `--px` в портрете **не** переопределён и остаётся
десктопным: при ширине 375 это 0,217 реального пикселя. Любое правило с
`calc(N * var(--px))`, которое портретный блок не перекрыл, рисуется в пятую
величину. Так навигация на странице кейса схлопывалась в 12 px, а маркеры
списка — в 2 px. Если на мобильном что-то выглядит крошечным, первым делом
ищите незакрытый `var(--px)`.

Тап-зоны. Пилюли тарифов и меню формата нарисованы на 34–41 px, пальцу нужно
44. Высота карточки расписана впритык, поэтому растёт не сама кнопка, а
невидимая зона вокруг неё — `::before` с `height: max(100%, 44px)`.

**Направление услуг выбирает системный список.** За пилюлей «Тарифы» стоит
обычный `<select>` на три пункта — Контент, Фото, Продакшн, — растянутый поверх
неё и прозрачный. Нажатие попадает по нему, и список открывает сама ОС: на
айфоне барабан Safari, на андроиде свой диалог. Он рисуется поверх страницы
средствами системы, поэтому ощущается частью телефона, а не сайта, и приносит с
собой прокрутку, жесты и доступность даром. Пилюля нарисована ровно по макету
(34 px при ширине экрана 375), запас до 44 держит сам контрол, а `font-size:
16px` на нём не даёт Safari зумить страницу по тапу.

Пикер свой у каждой карточки, а не один на активную: иначе при выборе React
уничтожал бы тот самый `<select>`, который пользователь только что трогал,
вместе с уходящей карточкой — а на телефоне поверх него в этот момент стоит
системный список. Невидимые карточки скрыты `display: none`, так что лишние
контролы не мешают ни глазу, ни скринридеру.

**Карточка живёт по содержимому и стоит по центру экрана.** Высоту ей ставит
`useServiceCardHeight` точным значением, а анимирует обычный CSS-переход: сам
CSS так не умеет, `transition` не работает при переходе к `height: auto`, и без
скрипта карточка прыгала бы рывком при смене тарифа. ResizeObserver, а не
разовый замер — высота меняется не только от выбора, но и когда переносится
строка после поворота экрана.

Неактивные карточки убраны из потока (`display: none`), иначе ячейка сетки
держала бы размер по самой длинной услуге и под коротким тарифом оставалась бы
пустота.

Переход задан селектором `.services__shell.reveal`: на шелле висит
`.reveal--scroll-card` со своим `transition`, и по специфичности он перебивал
одиночный `.services__shell` — высота менялась рывком.

Внутри — обычная колонка с шагом 16. Раньше здесь была сетка с `1fr` в
середине, чтобы плашка вставала ровно по центру; она же и давала провалы между
вкладками, плашкой и ценой.

**Кейсы идут обычным потоком.** Плитка 400×640, шаг 20 — как в макете. Своего
скролл-контейнера у ленты нет и быть не должно: раньше `.cases__grid` был
`overflow-y: auto` со `scroll-snap`, и внутри секции заводился второй скролл,
который перехватывал жест и не пускал страницу дальше. Вместе с ним убрана вся
логика выравнивания секции в `Cases.tsx` — она существовала только ради него.

**Меню формата** висит `position: fixed` внизу, пока секция кейсов в кадре.
Показывает его IntersectionObserver со сжатой областью наблюдения
(`rootMargin: '-40% 0px -40% 0px'`) — то есть по пересечению со средней пятой
частью экрана, а не по доле самой секции. Порог по доле здесь не работает:
лента из шести плиток выше трёх тысяч пикселей, в экран влезает от силы её
четверть, и прежние `threshold: 0.25` были физически недостижимы —
переключатель не появлялся вовсе. Сжатая полоса заодно даёт нужное поведение
на выходе: когда снизу приходит футер и занимает середину экрана, секция из
полосы выходит и меню уезжает вниз само.
Габариты трека — 240×150 в единицах макета, и это важно: от них посчитаны
смещения разлёта. В закрытом виде все три кружка лежат в центре пилюли со
`scale: .3`, при открытии разъезжаются в (210, 50), (120, 30) и (30, 50) по
кривой с перелётом, со сдвигом 0 / 0,05 / 0,1 с. Поэтому кружки позиционируются
через `left`/`top`, а не через `left: 50%` + `translate`: `translate` занят
анимацией.

Плитка кейса (макет `331:468`): кадр 400×640 целиком, подпись лежит на нём
снизу слева, справа — компактная пилюля со стрелкой вместо широкой кнопки.
Разметка кнопки одна на обе раскладки: на десктопе видна подпись, на мобильном
— стрелка. Под текстом только нижняя тень, а не затемнение всего кадра;
самостоятельным роликам она не нужна, и правило написано через
`:not(.case-tile--standalone)` — без него оно перебивает исключение из
`cases.css`, там специфичность такая же и решает порядок.

Число плиток совпадает с десктопом: показываются и самостоятельные ролики, у
них просто нет подписи — только кадр.

**Доводка блоков** (`useBlockSnap`). После остановки прокрутки страница
доезжает до блока, который занимает больше места на экране: Hero, услуги,
**каждая карточка кейса по отдельности**, футер. Секция, внутри которой есть
плитки, представлена не собой, а ими — иначе лента из шести карточек считалась
бы одним блоком и доводка перепрыгивала бы её целиком.

Анимация своя, а не `behavior: 'smooth'`: у родной прокрутки своя длительность,
которую нельзя настроить, и она заметно резче. Здесь 1150 мс с той же кривой
`easeInOutSine`, что у выравнивания секций на десктопе. Покадровый цикл живёт
только во время самой доводки, поэтому в покое телефону он не стоит ничего — в
отличие от полноценного перехвата прокрутки вроде Lenis.

Доводка отпускает, когда блок занимает меньше 0,3 экрана (у краёв документа
доехать до цели мешает его конец), и обрывается на любое касание, колесо или
клавишу, чтобы не бороться с пользователем.

**Выделение карточки.** Когда доводка встала на карточке кейса, её соседи
разъезжаются в стороны: верхние вверх, нижние вниз. Направление ставит хук
переменной `--spread-dir` (−1 / 0 / 1), величина живёт в `responsive.css`
рядом с остальной геометрией. На касание всё сходится обратно, на других
блоках сбрасывается.

Разводим именно трансформом, а не отступами: отступ над выделенной карточкой
сдвинул бы её саму вниз, и она слетела бы с центра, до которого только что
доехали. Трансформ вёрстку не трогает — высота страницы та же, карточка стоит
на месте, раздвигаются только соседи.

Сходятся карточки по действию пользователя, а не по событию прокрутки:
собственный tween сам их порождает, и на его хвосте выделение слетало бы сразу
после того, как встало.

Наклона плиток в портрете нет — он давал ровно то, что раздражало: карточка
кренилась на прокрутке и отыгрывала обратно. На десктопе наклон остался, а
секции там выравнивает `useSmoothScroll` через Lenis; `.cases` помечен
`data-free-scroll` и из выравнивания исключён — в сетке из трёх колонок
доводить до плитки бессмысленно.

**Грабли:** ориентацию оба хука проверяют по подписке на `matchMedia`, а не
один раз при монтировании. С разовой проверкой после поворота телефона наклон
пропадал до перезагрузки.

Футер живёт во фрейме `328:781` — в макете он по недоразумению назван «кейс».
Телефон там такая же карточка, как почта («Нажми и позвони»), поэтому классы
`.footer__mail-*` переиспользуются обеими. QR остаётся только на десктопе:
наводить камеру телефона на его же экран не на что. Обе разметки лежат в DOM
рядом, нужную показывает CSS.

**Страница кейса** (макет `278:2380`). Кадры идут столбцом во всю колонку в
пропорции 391×640, а описание и навигация уходят поверх них:

- остров с кнопками — `position: fixed` внизу, `z-index: 60`, всегда над
  контентом. Три кнопки: назад, «Описание», инстаграм; ник в остров не влезает,
  остаётся иконка. Снизу у страницы отдельный запас `120 * --mpx`, иначе остров
  накрывал бы последний кадр;
- кнопка «Описание» — два состояния: закрытая бирюзовая с подписью, открытая
  белая с крестиком. Оба лежат в разметке, нужное показывает CSS по классу на
  `.case-site`. Ширина одна на оба, иначе остров дёргался бы при открытии;
- описание — панель поверх кадров (`z-index: 50`), выезжает по кнопке;
- размытие фона — отдельный слой-подложка (`z-index: 40`), она же закрывает
  панель по тапу мимо. Именно отдельным слоем, а не фильтром на `.case-page`:
  фильтр создал бы containing block, и оба `fixed` внутри него перестали бы
  держаться за экран.

`.case-page__sidebar` на мобильном — `display: contents`: карточка и навигация
позиционируются от экрана сами, обёртка только мешала бы потоком. Карточке
нужен явный `width: auto` — ширина из десктопных стилей перебивает `right` и
растягивает панель мимо полей.

`useCaseScrollMotion` в портрете не запускается: ни наклонов, ни липкого
сайдбара макет не предполагает, а Lenis означал бы покадровый цикл на телефоне.
Ориентация — по подписке, чтобы поворот не оставлял состояние от предыдущей
раскладки.

## Постраничная прокрутка

Каждая секция занимает ровно `100vh` и держит по 60 сверху и снизу, поэтому
между содержимым соседних блоков ровно 120. Пользователь листает; как только
пройдено `TRIGGER` (80) пикселей из этих 120, следующий блок встаёт на место
предыдущего за `DURATION` (1.1 с) по пологой кривой.

Всё это в `src/hooks/useSmoothScroll.ts`. Саму прокрутку ведёт
[Lenis](https://github.com/darkroomengineering/lenis) — он двигает настоящий
скролл окна, поэтому `position: sticky` и замеры `getBoundingClientRect`
продолжают работать.

**Грабли:** `scroll-behavior: smooth` на `html` несовместим с покадровым
драйвером прокрутки — браузер начинает анимировать каждую запись позиции и
дерётся с ним. В `base.css` этого правила поэтому нет.

## Анимации

- **Hero** — восемь скошенных «плёнок» едут бесконечной лентой. При наведении
  лента замирает, карточка выезжает вверх и показывает «Открыть».
  Порядок наложения (левая поверх правой) не ломается на стыке петли:
  лента отрисована трижды подряд, а `z-index` убывает сквозь весь ряд.
- **«Мой подход»** — залипающий блок. Секция высотой 340vh служит «полосой
  разгона»: пока идёт прокрутка, сцена стоит на месте, текст держится в
  центре экрана и заливается побуквенно, а кейсы летят снизу вверх мимо
  него — часть по краям, часть за самим текстом.

  Карточки разложены по планам, и глубина задаёт сразу всё: ближние идут
  быстрее, ярче и строго в фокусе, дальние — медленнее, бледнее и в
  размытии (`filter: blur`). Отсюда и параллакс, и разделение планов. Те,
  что проходят сквозь текстовую колонку, самые дальние: размытие держит
  текст читаемым — затемнения под текстом нет.

  Слой с карточками растворяется у верхней и нижней кромки экрана
  (`mask-image`), иначе кадр обрезает их по прямой — на размытых планах
  это особенно заметно.

  Слова не набирают яркость плавно: голова прокрутки идёт по словам, и
  каждое вспыхивает целиком за 90 мс. Промежуточных состояний нет — слово
  либо погашено, либо горит.

  Тайминги подобраны так, чтобы в кадре всегда было 4–7 карточек, обе
  половины экрана заняты и хотя бы одна карточка была в фокусе; формула
  входа и выхода описана в шапке `src/data/approach.ts`. Прогресс считается
  в `useScrollProgress` и пишется прямо в DOM, без ререндеров React.

- **Плавная прокрутка с автодоводкой блоков** (`useSmoothScroll`) — саму
  прокрутку ведёт [Lenis](https://github.com/darkroomengineering/lenis): он
  перехватывает колесо, гонит страницу по кадрам с инерцией и корректно
  ладит с `position: sticky`, потому что двигает настоящий скролл окна.

  **Грабли, на которые тут легко наступить:** `scroll-behavior: smooth` на
  `html` несовместим с любым покадровым драйвером прокрутки — браузер
  начинает анимировать каждую запись позиции и дерётся с ним. Поэтому в
  `base.css` этого правила нет, а якорные переходы ведёт сам Lenis через
  опцию `anchors`.

  Доводка сделана как помощь, а не как перехват управления:

  1. Срабатывает не посреди жеста, а когда пользователь остановился и
     инерция улеглась (`IDLE`). Пока крутишь — страница слушается только тебя.
  2. Едет по кривой ease-in-out: трогается с нуля и мягко тормозит.
     Длительность зависит от расстояния, поэтому короткая доводка не
     выглядит вялой, а длинная — суетливой.
  3. Отменяется мгновенно от колеса, клавиши или клика по полосе.
  4. Работает только внутри полосы `BAND` от верха экрана. Если блок ещё
     еле выглядывает снизу — не трогаем.

  Пункт 4 важен: блок услуг (721px) короче экрана (820px), поэтому после
  посадки следующий блок торчит снизу на 99px. Он вне полосы, и подряд
  идущие доводки не сцепляются — между блоками можно спокойно стоять.
  У секций свои 60 сверху и снизу, поэтому в кадре содержимое оказывается
  ровно в этой рамке.

  Ловим только движение вниз: вверх страница листается свободно, иначе
  доводка выбрасывала бы из «Моего подхода» целиком.

  | константа | сейчас | что делает |
  |---|---|---|
  | `LERP` | 0.085 | тягучесть прокрутки: меньше — дольше догоняет |
  | `WHEEL` | 0.85 | множитель колеса: меньше — мягче шаг |
  | `IDLE` | 220 | сколько тишины ждём после жеста, мс |
  | `BAND` | 0.75 | доля экрана, ниже которой блок не трогаем |
  | `SNAP_DURATION` | 1.4 | длительность доводки, с |

  Клавиатура, полоса прокрутки и якорные ссылки работают штатно. На
  тач-экранах и при `prefers-reduced-motion` хук не включается — родная
  инерция лучше.
- **«Услуги»** — высота блока 900, по 60 сверху и снизу, значит контент 780.
  Плейсхолдеры справа растянуты на все 780. Содержимое карточки слева идёт
  сплошным потоком с одинаковым шагом 20 (10 у пар «подсказка → пилюли» и
  «Цена: → сумма») и заканчивается там, где заканчивается — распорки между
  списком и ценой нет. Если тариф короткий, свободное место остаётся внизу
  колонки. Содержимое при переключении проявляется снизу вверх.
- **«Кейсы»** — переключатель формата перестраивает сетку с каскадом.

Всё уважает `prefers-reduced-motion`.
